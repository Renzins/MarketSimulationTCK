# TCK Market Dashboard — Backtester + BESS + Spread Graphs + Forecast

A static, four-page web tool (UI brand **"TCK Market Dashboard"**) for
the Vanessa / Targale wind park (14 × 4.2 MW = 58.8 MW, Latvia). No
server, no build step, no install — every page is plain HTML + JS served
as-is. (The Backtester page is titled **"Backtester - Wind Park"** in the
navbar.)

The **Backtester** and **Graphs** pages run **entirely client-side and
offline**: embedded datasets (~3 MB main + ~1.2 MB aFRR + ~85 MB
lazy-loaded per-4-s spread) drive all simulation in the browser. The
**Forecast** page is the one exception that touches the network — it
reads a live `forecast.json` (and can trigger a fresh model run) from a
separate **private** repo via the GitHub API; see "Forecast" below.

The tool is split into four pages, navigable from a top navbar:

| Page              | What it does                                                                                  |
| ----------------- | --------------------------------------------------------------------------------------------- |
| **Backtester - Wind Park** | Strategy P&L over a configurable simulation window, with a **day-type filter** (all / weekends+holidays / workdays). A unified engine runs **five toggleable, jointly-optimised strategies**: **reserve-market** capacity (down), **DA-withhold on low prices**, **adaptive mFRR↔aFRR split**, **ID-trust**, and **intra-day oversell + hedge-mFRR-dn (S3)**. Each ⚡ Optimise is logged to an **Optimised-runs** comparison table (persists per browser tab). |
| **Backtester - BESS** | Grid-scale **battery** (default 40 MWh / 20 MW) trading DA / mFRR / aFRR / intraday. A **stateful** 15-min simulation: state-of-charge is *carried* across periods. Five toggleable strategies — **adaptive mFRR↔aFRR split** (carried over), **sell-on-DA**, **dynamic multi-source charging**, **dynamic discharge pricing**, **opportunistic balancing override** — over an operating band (red zones), a round-trip-margin gate (min delta) and a must-fulfil guarantee on balancing activations. Same optimiser + Optimised-runs log. See [Backtester — BESS](#backtester--bess). |
| **Graphs**        | Box plots and heatmaps over four sub-tabs: **mFRR** spread, **aFRR** spread/activation, **mFRR vs aFRR** (joint slot-level analysis), and **mFRR vs aFRR reserves** (daily reserve-capacity-price dynamics + imbalance-risk link). |
| **Forecast**      | Six-hour-ahead (24 × 15-min) probability forecast of Baltic imbalance regimes — NEG (deficit) / ZRO (balanced) / POS (surplus) — plus expected imbalance prices. The model lives in a private repo; the page reads its `forecast.json`, and a single button dispatches a fresh run via GitHub Actions, then redraws when it lands. A completed run is cached per browser tab so navigating away and back keeps it on screen. |

## Backtester — strategy & sign conventions

Per ISP (15-min period). Energy = MW × 0.25 h. Positive = money to the park.

```
DA revenue       =   Q_da_sold * P_da                  (≥ 0)
mFRR-up rev      =   Q_up_mfrr * P_mfrr                (+ when P_mfrr > 0)
mFRR-dn rev      = − Q_dn_mfrr * P_mfrr                (+ when P_mfrr < 0)
aFRR-up rev      =   Q_up_afrr * avg_p_pos             (+ when avg_p_pos > 0)
aFRR-dn rev      = − Q_dn_afrr * avg_p_neg             (+ when avg_p_neg < 0)
Imbalance cost   = − Q_short   * P_imb                 (cost when short)
Flat penalty     = − Q_short   * θ_flat
ISP P&L          = (DA + mFRR-up + mFRR-dn + aFRR-up + aFRR-dn − imb − flat) × 0.25
```

### Market activation — gates per market and direction

```
mFRR (per-ISP, binary):
  P_mfrr ≥  1   → mFRR-up activates  (offer = Q_w + max(0, Z·(ID − DA)))
  P_mfrr ≤ −1  → mFRR-dn activates  (offer = Q_da_sold)
  otherwise   → mFRR offer earns 0

aFRR (per-ISP, profitability gate; partial dispatch averaged across the ISP):
  avg_p_pos > 0 → aFRR-up active  (revenue uses Q_up_afrr)
  avg_p_neg < 0 → aFRR-dn active  (system pays park; −Q × negative = positive)
  otherwise   → that direction earns 0 (the wind park wouldn't have bid)
```

The `avg_p_pos > 0 / avg_p_neg < 0` gates are at ISP granularity. They
hold by construction once `data-afrr-15min.js` is built with the
favourable-only filter (see "aFRR market"): `avg_p_pos ≥ 0` and
`avg_p_neg ≤ 0` dataset-wide.

### mFRR ↔ aFRR adaptive offer split

For each direction we route part of the offered MW to mFRR and the
remainder to aFRR (whole-MW round-and-remainder, no MW lost):

```
Q_up_mfrr = round(s_up · Q_up_offer)     Q_up_afrr = Q_up_offer − Q_up_mfrr
Q_dn_mfrr = round(s_dn · Q_dn_offer)     Q_dn_afrr = Q_dn_offer − Q_dn_mfrr
```

But `s_up` / `s_dn` are no longer constants — they **adapt over time,
per direction**, with **four** params each: **start `x`**, **lookback
window `y`** (ISPs), **rebalance wait `w`** (ISPs), **step `z`**. The
split begins at `x`; every `w` ISPs (the **cadence**) it compares the
average per-MW revenue *rate* of the two markets over the **trailing `y`
ISPs** (the **lookback**) and steps toward the winner by `z`:

```
up rate:  mFRR = p_mfrr when it clears up (≥1) else 0 ;  aFRR = avg_p_pos
dn rate:  mFRR = −p_mfrr when it clears dn (≤−1) else 0;  aFRR = −avg_p_neg
mFRR wins → s += z   ·   aFRR wins → s −= z   ·   tie → no move   ·   clamp [0,1]
```

`w` (cadence) and `y` (lookback) are **decoupled**: `w = 1` (the default)
re-evaluates *every ISP* off a sliding `y`-ISP window — responsive *and*
stable; `w = y` reproduces the original non-overlapping block behaviour.
The adaptation is **causal** (each step uses only past prices) and runs
continuously from the dataset start (like the S3 rolling stats), so a
sub-window inherits the right split state; a winsor-keyed prefix-sum
cache (`_splitEffPrefix`) keeps the optimiser fast. All eight params
(`x₁ y₁ w₁ z₁` up, `x₂ y₂ w₂ z₂` down) are swept by the optimiser.

**`z = 0` ⇒ the split never moves ⇒ static split at `x`** — the engine
collapses to the pre-feature behaviour, so `x = 1, z = 0` (the default)
reproduces the old all-mFRR default and the frozen regression values
hold exactly (`test_split_adaptive_step0_equals_static`). The static
scalar `s_up`/`s_dn` call path is retained in the engine + Python mirror
for those anchors. Up and down are independent because the per-direction
price economics aren't symmetric.

### Position accounting

```
Q_position  = Q_da_sold
            + (mFRR-up active ? Q_up_mfrr : 0)         + Q_up_afrr × n_pos_fav/225
            − (mFRR-dn active ? Q_dn_mfrr : 0)         − Q_dn_afrr × n_neg_fav/225

Q_short     = max(0, Q_position − Q_pot)
```

mFRR contributes its full Q when activated (binary across the ISP).
aFRR contributes a time-fraction `n_*_fav / 225` — the count of 4-s
slots where the price was favourable for that direction — same factor
that makes the revenue formula correct.

### Reserve market — up capacity (carved before everything)

A toggleable **Reserve market — up capacity** card sits *above* the
down-capacity card (default **OFF**) and models winning *upward*
balancing-capacity. Data: hourly LV `reserves_mfrr_upward_lv` /
`reserves_afrr_upward_lv` prices (EUR/MW·h), in `data-reserve.js`. Same
three parameters as down — `ru_coef`, `ru_split`, `ru_min_price` — **plus
one more**:

- **Min forecast MW** `ru_min_mw` — only offer up capacity in ISPs where
  the DA forecast ≥ this many MW (so the park doesn't commit upward reserve
  when there's little forecast wind to ramp into). **Swept** by the optimiser.

The crucial difference from down: **up capacity is not free money.** Each
awarded MW is *withheld from DA* — it is the head-room the park would ramp
into if the TSO activates upward — so it shrinks the forecast available for
DA + down capacity. Per ISP (award `R_up = R_up_mfrr + R_up_afrr`,
whole-MW, each product kept only if `F ≥ ru_min_mw` and its winsorized
price is finite and ≥ min):

```
R_up                 = floor(ru_coef × F)              # gated by ru_min_mw + price
F_avail              = F − R_up                         # ← DA and DOWN capacity can only use this
capacity income      = (R_up_mfrr·p_res_mfrr_up + R_up_afrr·p_res_afrr_up) × 0.25
da_sold              = max(withhold(F_avail), R_dn)     # ≤ F_avail
Q_w (free up offer)  = floor(F) − R_up − da_sold        # ≥ 0
up offer (mFRR/aFRR) : reserve MW use ru_split (a MANDATORY floor); the free Q_w uses s_up
                       ⇒ total up offer == R_up + free
```

Down capacity is then sized **within `F_avail`** (`floor(r_coef × F_avail)`),
so `R_up + da_sold ≤ floor(F)` always holds — the worked example (20 MW
forecast, offer 10 MW up ⇒ DA + down capacity ≤ 10 MW) falls straight out.
The award is **mandatory regardless of wind**: when up-activated the `R_up`
MW enter the position, so a low-wind ISP can fall short and pay imbalance —
a risk the (always-curtailable) down capacity doesn't carry. With the box
off (`R_up = 0`, `F_avail = F`) every line collapses to the down-only math,
so the frozen L3 is byte-identical (locked by
`test_reserve_up_off_equals_l3_default`). Up income shows in the tooltip and
as a distinct lighter-gold monthly stack; the decomposition table splits
**Reserve cap (up)** / **Reserve cap (dn)**. JS↔Python parity holds to
float32 drift (full-config check: 17,183,516 € oracle vs 17,183,511 €
engine). Like `r_coef`, the swept `ru_coef` saturates toward 1.0 in
isolation (no price-impact model) — treat it as a liquidity lever and gate
with `ru_min_mw` / `ru_min_price`.

### Reserve market — down capacity (sits before day-ahead)

A toggleable **Reserve market** card (below the up-capacity card, default
**OFF**) models winning balancing-capacity in the auction that clears
*before* day-ahead. This is the **down** side (the up side is the separate
card above); the awarded MW are sized within the forecast left after any up
capacity (`F_avail`). Data: hourly LV `reserves_mfrr_downward_lv` /
`reserves_afrr_downward_lv` prices (EUR/MW·h), shipped in `data-reserve.js`
(see Data layout). Parameters:

- **DA offer coefficient** `r_coef` — awarded MW = `floor(r_coef × F)`.
- **mFRR ↔ aFRR reserve split** `r_split` — routes the award between the
  two reserve products (each paid its own capacity price).
- **Min reserve price** `r_min_price` — per-product reservation floor; a
  product priced below it is treated as not awarded that ISP. **NOT
  swept** by the optimiser (the others are).

Per ISP, with award `R = R_mfrr + R_afrr` (whole-MW, each product kept
only if its winsorized price is finite and ≥ min):

```
capacity income      = (R_mfrr·p_res_mfrr + R_afrr·p_res_afrr) × 0.25   (EUR, confirmed settlement)
da_sold              = max(withhold-level, R)        # reserve MW are MANDATORY DA sales
Q_w (up offer)       = floor(F) − da_sold
down offer (mFRR/aFRR): reserve MW use r_split; the non-reserve da_sold−R uses s_dn
                        ⇒ total down offer == da_sold (unchanged)
```

The elegance — and the reason it can't break the audited engine — is
that **with the box off (R = 0) every line collapses to the pre-reserve
math**, so the frozen L1/L2/L3 values are byte-identical (locked by
`test_reserve_off_equals_l3_default`). Reserve only (a) adds the capacity
income leg, (b) raises the DA floor so the awarded MW bypass the withhold
rule (hence the card rename to *"DA withhold on low prices (non-reserve
volume)"*), and (c) re-routes a slice of the down offer to the reserve
split. Down activation still uses our own price gates. Income shows in
the time-series tooltip (no extra bar) and as a distinct gold stack in
the monthly decomposition.

⚠ **Backtest caveat (same shape as S3 `X_cap`):** the optimiser sweeps
`r_coef`, which **saturates to 1.0** — with no price-impact / auction-
clearing model, offering more capacity is always net-positive. Treat
`r_coef` like `X_cap` (a liquidity lever) and use `r_min_price` to gate
participation; the `r_split` optimum leans toward aFRR because the
aFRR-down capacity price has a fat right tail (high winsorized mean).

### Physical constraints (audit-applied)

1. **Whole-MW market quantities.** Balancing market accepts integer-MW
   blocks only, so `Q_da_sold`, `Q_w`, `trusted_rev` and `Q_dn_offer`
   are floored. The `s_up` / `s_dn` split also produces whole-MW
   `Q_*_mfrr` and `Q_*_afrr` (round + remainder).
2. **mFRR-dn capped at the DA position.** A wind park can drop from
   `Q_da_sold` to 0 but cannot go below 0. Therefore
   `Q_dn_offer = Q_da_sold` (independent of Y), and when `Q_da_sold = 0`
   no mFRR-dn or aFRR-dn revenue is possible.
3. **Position decreases when downward fires.** When mFRR-dn activates,
   promised production drops by `Q_dn_mfrr`; when aFRR-dn fires
   profitably it drops by `Q_dn_afrr × n_neg_fav/225`. Both terms
   appear with a minus sign in `Q_position`.
4. **mFRR up vs dn mutually exclusive per ISP** (P_mfrr is
   single-signed). mFRR-up vs aFRR-up vs aFRR-dn vs mFRR-dn can co-fire
   freely if their respective gates pass — different MW pools.

## Level 3 — speculative intra-day oversell (S3)

L3 sits on top of L2 (same DA / mFRR / aFRR / imbalance math) and adds
**a per-ISP speculative leg**: when our rolling forecast of the next
ISP's mFRR clearing price is sufficiently below `VWAP1H`, we oversell
up to `X_cap` extra MW on intra-day AND submit a **hedge mFRR-dn bid**
at `VWAP1H + M`. The hedge bid is a stop-loss mFRR-dn offer the wind
park wouldn't normally place — pitched above the typical clearing — so
when it clears it costs us, but it caps the worst-case loss on the
oversold volume at `bid_price · X` per MWh (vs being exposed to
potentially much higher imbalance settlement).

The rolling stats are taken over **`p_mfrr[H − K − L : H − L]`** (raw,
unwinsorized). The lag `L` (default 4 ISPs ≈ 1 hour) models the
real-world publication latency: at 08:55 a trader bidding for the
09:30 ISP can only see settlement prices through ~08:30. Setting `L = 0`
reproduces the legacy no-lag behaviour. `L` is a manually-set
parameter, **not optimised**. Earlier builds used `p_imb` rather than
`p_mfrr` — `p_imb` is the price the wind park *would have paid if
short*, not the actual signal a real trader uses to time an intra-day
oversell; switching to `p_mfrr` aligns the gate with what's observable.

### Algorithm (per ISP H)

```
INPUTS:  VWAP1H[H], p_mfrr[H-K-L : H-L]  (raw, NaN-aware)
PARAMS:  K, L, DA_skip, S_min, sigma_max, X_cap, M
GATES:
  G0: da_sold[H] < DA_skip                            (else skip S3 entirely)
  G1: spread  = VWAP1H[H] − mean(p_mfrr[H-K-L : H-L]) >= S_min
  G2: sigma   = std(p_mfrr[H-K-L : H-L])              <= sigma_max
  G3: X_prop  = floor(X_cap · min(1, (spread - S_min) / S_min)) >= 1
  G4: VWAP1H[H], rolling stats not NaN (need H ≥ K + L)
IF ALL GATES PASS:
  bid_price        = VWAP1H[H] + M
  intraday_rev     = X_prop · VWAP1H[H]                    (always)
  hedge_clears     = p_mfrr[H] <= bid_price                (NB sign!)
  IF hedge_clears:
    curtail_rev    = X_prop · (−p_mfrr[H])                 (signed)
    Q_position    += 0   (curtailment offsets oversell)
  ELSE:
    Q_position    += X_prop                                (shortfall grows)
```

### Sign convention for the hedge bid

`p_mfrr` is **unified across directions** (Latvia single clearing).
A hedge mFRR-dn bid at `bid_price` clears whenever the marginal price
is no more than our ceiling — i.e. `p_mfrr ≤ bid_price`. This is the
stop-loss framing:

- `p_mfrr ≪ 0` (very negative): grid pays us `|p_mfrr|` per MWh
  curtailed — **windfall**.
- `0 < p_mfrr ≤ bid_price`: we pay the grid `p_mfrr` per MWh curtailed
  — **bounded loss** (capped at `bid_price · X` per MWh, cheaper than
  imbalance would have been).
- `p_mfrr > bid_price`: bid doesn't clear; we're exposed to the
  imbalance settlement.

### Unified optimiser

**One ⚡ Optimise button** sweeps every optimised parameter of the
**enabled** strategies jointly. With all six on that's up to **20
dimensions**: reserve-up `(ru_coef, ru_split, ru_min_mw)`, reserve-down
`(r_coef, r_split)`, DA-withhold `(X, Y)`, adaptive split `(x₁, y₁, w₁, z₁,
x₂, y₂, w₂, z₂)`, ID-trust `(Z)`, and S3 `(K, S_min, σ_max, M)`. Disabling a
strategy drops its dimensions; both min-reserve-prices,
S3 `X_cap` / lag `L` / `DA_skip` are held at the user's values because
they're physical / liquidity constraints, not strategy levers (see
"Known quirks" #18). More enabled strategies ⇒ a heavier sweep, so
disable the ones you're not studying to keep Optimise snappy.

The algorithm is **seeded random search + multi-start coord-descent
refine**:

1. Draw N = 4000 uniform random samples over the optimised parameter
   space. Track the top-K samples by revenue (sorted insertion into a
   small array — K = 5).
2. For each of the top-K samples, run coordinate-descent refine:
   sweep each axis over its grid holding others at the current best,
   update the best, repeat for up to 3 passes (stop early if a full
   pass yielded no improvement).
3. Return the highest-revenue refined sample.

The objective is the **filtered** total (it honours the active day-type
filter), so "Workdays only" and "Weekends + holidays" produce distinct
optima you can compare.

After the refine phase, every Optimise also runs the **parameter
sensitivity analysis** (adds ~20 % to the runtime): OAT weight /
1 %-band / shape / edge per optimised parameter, global Spearman ρ +
top-decile clustering over the 4 000 random samples, and the pairwise
interaction ranking with a 2-D sweep of the strongest pair — rendered in
the "Parameter sensitivity" card above the runs log. The method (and its
caveats) is documented once, in the BESS section:
[Parameter sensitivity — reading an optimum honestly]
(#parameter-sensitivity--reading-an-optimum-honestly); the math +
renderers are the shared `optim-sens.js`. The headless `__optimiseSilent`
debug hook intentionally skips the analysis (variance experiments stay
lean).

### Optimised runs log

Below the charts, an **Optimised runs** table logs one row per completed
Optimise: the setup (sim window, day-type filter, sources, winsor pairs,
θ), which strategies were enabled, the optimal parameters found, the run's
**top drivers** (the three heaviest parameters from the sensitivity
analysis, ⚠ = saturated at a sweep edge), and the resulting revenue vs the
naïve baseline. It's purpose-built for comparing configurations side by
side — e.g. whether summer and winter, or workdays and weekends, prefer
different parameters, and whether two "different" optima actually differ
only in weightless parameters. Newest run on top; **Clear** empties it.

The log is **persisted per-tab** in `sessionStorage`
(`tck.optimRuns.v1`): it survives navigating to Graphs / Forecast and
back (and same-tab reloads), and is wiped only when the tab is closed.
Writes are best-effort (wrapped in try/catch, so a disabled/full store
just degrades to in-memory). See [Per-tab caching](#per-tab-caching).

**Why multi-start?** A variance test (3 RNG seeds × 3 levels) found
near-zero spread (<0.07 % on L1 / L2, 0 € on L3) — the landscape
on the current dataset has one dominant basin and refine converges
reliably from a wide range of starting points. Multi-start is
**belt-and-suspenders** against future data introducing additional
basins: if a second basin appears with a competitive optimum, top-K
will include samples from both, refining catches both, and we
return the better one.

**Per-level config** (measured per-sim costs: L1 0.65 ms, L2 1.26 ms,
L3 2.10 ms — L3 is dearer because S3's rolling stats run per-ISP):

| Level | N    | K | Random | Refine (K × ~)   | Wall  |
|-------|------|---|--------|------------------|-------|
| L1    | 2000 | 3 | 1.3 s  | 3 × 0.4 s = 1.2s | 2.5 s |

| L3    | 4000 | 5 | 8.4 s  | 5 × 3 s   = 15s  | 23 s  |

**Reproducibility**: a seeded Mulberry32 PRNG (default seed
`0xC0FFEE`) drives all sampling, so clicking Optimise twice on the
same Setup produces identical results. The debug hook
`window.__optimiseSilent(level, seed)` runs the same logic with a
chosen seed and returns `{revenue, sample, ms}` without touching the

**UI yielding**: the optimiser cooperatively yields every 200 ms via
`MessageChannel.postMessage` (faster than `setTimeout(0)`, which gets
throttled in some browser contexts). Both the random loop and the
inner refine loop carry yields, so the UI stays responsive even
during the 15 s of refine on L3.

### ⚠ Backtest caveat — S3 scales infinitely because price impact isn't modelled

A real, documented finding: with `X_cap` left in the sweep, the
optimum would have landed on the grid maximum every time — selling more
is always net-positive on this dataset. We responded by **pinning
`X_cap` out of the sweep entirely** (see "Dual optimisers" above);
`S_min` and `σ_max` still sometimes settle on the grid edge. The
interior dimensions (`K ≈ 4`, `M ≈ 5`) are genuine optima.

**Why the boundary-optimum is real but unactionable**:

1. **The strategy formula correctly identifies the right opportunities.**
   At every triggered ISP, the model picks "high expected ID-vs-imbalance
   spread in a stable regime". The S_min / σ_max filters are doing their
   job; the optimum simply discovers that, on this dataset, *more*
   opportunities than the defaults gate is profitable.
2. **The backtest has no price-impact term.** Selling 30 MW into the
   Latvian intra-day market would push `VWAP1H` against you, eroding
   the spread the strategy depends on. The model assumes infinite
   liquidity at the quoted VWAP.
3. **No execution fees / spreads**, no counterparty / TSO ratification
   risk, no capacity constraints beyond `X_cap` itself.

Operational reading: the formula is sound for **identifying when** to
oversell; **how much** to oversell needs a separate (out-of-scope)
price-impact model. Recommended manual values for in-the-real-world
use: `S_min = 15–25`, `σ_max = 75–150`, `X_cap = 5–10` MW.

## aFRR market — averaged 15-min prices, favourable-only filter, gates

aFRR runs at 4-second cadence in real life. Pricing every 4-s slot
inside the per-ISP simulation would be too slow for the Backtester's
parameter sweeps, so we **pre-average** AST_POS / AST_NEG to one
number per 15-min ISP via `preprocess-afrr-15min.py`. Two important
twists:

### Favourable-only filter (preprocess-afrr-15min.py)

A wind park bidding sensibly only accepts activation when the price
favours its direction. Inside a single 15-min ISP, the 4-s prices can
swing sign — e.g. AST_NEG = `{−10 €/MWh, +50 €/MWh, NaN×223}`. A
naïve average gives `+0.18 €/MWh`, the engine's gate then drops the
entire ISP, and the wind park loses the `1 MW × 4 s × 10 €/MWh =
0.011 €/MW` it would actually have earned during the favourable slot.

The fix is to filter before averaging:

```
AST_POS values ≤ 0   →  replaced by 0  (we wouldn't bid into money-losing upward)
AST_NEG values ≥ 0   →  replaced by 0  (we wouldn't pay to curtail)
```

After the filter, by construction:
- `avg_p_pos[i] ≥ 0` for every i
- `avg_p_neg[i] ≤ 0` for every i
- the per-direction profitability gate (`avg_p_pos > 0` / `avg_p_neg < 0`)
  is equivalent to "at least one favourable 4-s slot existed in this ISP"

The same filter drives two **favourable counts**:
- `n_pos_fav[i]` — count of 4-s slots in ISP i where AST_POS > 0
- `n_neg_fav[i]` — count of 4-s slots where AST_NEG < 0

These scale the L2 position contribution: dispatched MW =
`Q_*_afrr × n_*_fav / 225`. Distinct from `data-afrr.js`'s `n_pos`
/ `n_neg`, which count ALL non-NaN slots regardless of sign.

### Revenue formula derivation

A 4-s slot's energy share of an ISP is `4/3600` hours, and an ISP is
`0.25` hours. So if a single 4-s slot fires upward at 900 €/MWh and
the rest are NaN:

```
revenue per offered MW
  = 1 MW × 900 €/MWh × (4 s / 3600 s)
  = 1 €
```

With our averaged price:

```
avg_p_pos = max(0, 900) / 225 = 4 €/MWh
revenue per offered MW = 1 MW × 4 €/MWh × 0.25 h = 1 €  ✓
```

The same `1/225` factor appears in the position contribution
(`Q_afrr × n_*_fav / 225`), so revenue and position stay consistent.

### Why the optimiser finds asymmetric optima on this dataset

For this Vanessa data (after the filter):
- median `avg_p_pos` ≈ +16.7 €/MWh — aFRR-up earns continuously, often
  more than mFRR-up's spike-driven earnings
- median `avg_p_neg` = 0 (most ISPs no favourable downward slots);
  when there ARE, the magnitudes are large

The L1 optimiser at default X / Y typically picks `s_up ≈ 0` (route
upward to aFRR) and `s_dn ≈ 1` (keep downward in mFRR), recovering
~150 k € over the symmetric-mFRR baseline. Your dataset may differ —
the per-direction split exists precisely so the optimiser can find
the right mix.

## Backtester — BESS

`bess.html` + `bess-engine.js` + `bess-charts.js` + `bess-app.js`. A grid-scale
**battery** (default **40 MWh / 20 MW**) trading the same Latvian markets the
wind-park page uses — day-ahead, mFRR, aFRR, intraday — plus the imbalance
fallback. It loads `engine.js` purely for its shared utilities (`Engine.init`
builds the typed arrays, day-type mask and winsorised price buffers); the
state-of-charge simulation itself is all in `BessEngine`.

### Why it is a separate, stateful engine

The wind-park engine treats every ISP as **independent**. A battery cannot:
**state-of-charge (SoC) is carried** — energy discharged now is energy you can't
discharge later. So `bess-engine.js` is a **sequential** simulation with a
running SoC, a running **cost basis**, and a running operating **mode**. One
core loop `_run(params, detail)` feeds both `simulate()` (full per-ISP detail +
bid log + ops/SoC stats) and `simulateTotal()` (fast, optimiser hot path) — a
single code path so the two can never diverge (locked by a parity test).

### Setup (experiment environment — NOT optimised, NOT reset)

The wind-park's actual-power / intra-day-power source selectors and reserve
winsorisation are **removed** (a battery has no generation forecast). What's
kept: sim date range, day-type filter, mFRR / imbalance / aFRR-up / aFRR-dn
winsor, θ_flat. New battery parameters:

| Param | Default | Role |
| ----- | ------- | ---- |
| Battery capacity | 40 MWh | SoC bound `[0, cap]` |
| Max power | 20 MW | inverter limit; grid-side `eMax = Pmax × 0.25 h` per ISP |
| Round-trip efficiency | 90 % | `etaLeg = √η` applied each leg, grid-side |
| Initial SoC | 50 % | SoC at the first ISP of the window (treated as zero-cost) |
| Min time between direction change | 4 ISPs (1 h) | cooldown/rest: ≥ this many idle ISPs since the last action before flipping to the OPPOSITE direction (measured from a block's END, so it forces a real break between phases; DA commitments exempt) |
| Upper red zone | 80 % | stop placing new **charge** bids above this |
| Lower red zone | 20 % | stop placing new discretionary **discharge** bids below this |
| Min delta | 100 €/MWh | required round-trip margin per delivered MWh |
| θ_flat | 30 €/MWh | flat penalty on **unmet DA** MWh (balancing is never unmet) |

### Sign conventions, efficiency and the min-delta gate

Energy `E = MW × 0.25 h`; price €/MWh; **+ = money in**.

```
DA discharge    +E · p_da                          (sell stored energy to DA)
mFRR-up         +E · p_mfrr      (p_mfrr ≥ +1)      (discharge into balancing)
aFRR-up         +E · avg_p_pos   (avg_p_pos > 0)    (partial dispatch n_pos_fav/225)
mFRR-dn charge  −E · p_mfrr      (p_mfrr ≤ −1)      (charge; p<0 ⇒ PAID to absorb ⇒ +)
aFRR-dn charge  −E · avg_p_neg   (avg_p_neg < 0)    (partial dispatch n_neg_fav/225)
intraday charge −E · vwap                           (real-time charge; vwap<0 ⇒ income)
DA buy-low      −E · p_da                           (day-ahead committed trough buy)
opportunistic   close diverted DA on INTRADAY: −E · vwap   (DA revenue is KEPT)
DA shortfall    −E_short · (p_imb + θ)              (unmet DA settles at imbalance)
```

### Information timing — no future leakage

ISP `i` covers `[t0, t0+15)`. The market gates, and what is knowable at each:

| Gate | Closes | Newest settled balancing ISP | Also known |
| ---- | ------ | ---------------------------- | ---------- |
| Day-ahead | D−1 auction | — | own DA clearing (price + volume) |
| Intraday | t0−30 (= end of ISP i−3) | **i−3** | `vwap_1h` — a NordPool snapshot taken 1 h before delivery, treated as an executable quote |
| mFRR/aFRR bids | t0−25 (ISP i−2 still running) | **i−3** | own intraday fills (they happened at t0−30) |
| Imbalance | settles after delivery | — | never known at bid time |

The rule enforced throughout the engine: **every decision — direction, sizing,
routing, re-pricing, the opportunistic divert — reads settled prices (≤ i−3)
plus the live intraday quote; the current ISP's realised mFRR/aFRR prices
decide only whether a placed, priced bid clears** (standard bid mechanics: an
offer at ask X clears iff the clearing price reaches X — that is not
clairvoyance). Consequences worth knowing:

- **Placement is a posture**: offers go out whenever physically possible and
  rest unfilled if the market never reaches them. When both directions are
  physically possible, the side is picked by comparing *known* richness
  (settled balancing prices / live intraday quote) — never the current ISP's.
- **Charge routing** re-routes a share to the other balancing side only when
  its own side was unusable in the last *settled* ISP, and intraday takes the
  headroom only when settled balancing was dead entirely — the old engine
  routed by the current ISP's realised prices (that was look-ahead, worth
  roughly a third of the P&L; see the numbers below).
- **The opportunistic divert is a committed bet**: triggered by the settled
  spike (`p_mfrr[i−3] − Vwap ≥ threshold`), the intraday buy-back is paid
  either way; the freed energy is offered to mFRR at `Vwap + threshold` and
  can MISS — the energy stays stored and the ISP nets `DA − intraday`
  (counted as "Divert misses").
- **Imbalance is never a chosen close**; it only arises passively when a DA
  delivery physically falls short. **Day-ahead can only be committed a day
  before**, so DA buy-low is a committed forecast-trough leg, not a real-time
  charge source.
- Locked by `test_no_future_leakage_perturbation`: shocking the current ISP's
  realised balancing prices must change **nothing** that was placed for that
  ISP (direction, products, MW, intraday volume, DA delivery, divert
  commitment) — only clearing outcomes may differ.
- Under fair timing the same default config re-measures from **3.10 M€ to
  2.03 M€ (−34 %)** — that gap was the look-ahead premium of the old
  clairvoyant routing/direction/divert logic, now removed. (The shipped
  default lands at **2.11 M€** after also dropping the harmful switch — see
  the re-pricing section.)

Efficiency is split √η per leg, grid-side: charging `g` MWh raises SoC by
`g·√η`; delivering `d` MWh drops SoC by `d/√η`. The **cost basis** is the
weighted-average €/MWh *stored*; charging `g` at `price` updates it to
`(cb·soc + price·g)/(soc + g·√η)`. The **break-even delivered sell price** is
`effCost = costBasis / √η` (it includes the discharge loss), so a discretionary
discharge fires only when `sell ≥ effCost + minDelta`. That makes "min delta" a
**true round-trip margin** per delivered MWh — charging at a negative price (or
buying cheap) lowers the basis and the bar a later discharge must clear.

### Red zones + the must-fulfil guarantee

Discretionary **new** offers keep SoC inside `[lowerRed, upperRed]·cap`. The
`[0, lowerRed]` and `[upperRed, cap]` buffers exist so a *committed* activation
can use them without the strategy over-committing. Every balancing offer
(mFRR/aFRR, both directions) is sized so the dispatched energy is always
deliverable within physical `[0, cap]` and the power limit — therefore **a
committed balancing activation is never short** (the SoC-safety audit confirms
`unfulfilled = 0`). Only **day-ahead** positions are ever allowed to fall short
→ they settle at `p_imb + θ`, exactly as specified ("imbalance from unfulfilled
DA is fine; failing a balancing activation is not").

### Day-ahead price forecast (lag-24h)

DA is committed a day in advance, so the strategy can't see tomorrow's price. It
uses a **lag-24h (96-ISP) persistence forecast**: `forecast[i] = p_da[i−96]`.
Within each UTC day the ISPs are ranked by that forecast and the top
`da_n_periods` are targeted for discharge; the offer (floor `da_min_price`)
clears at delivery iff the **actual** `p_da ≥ floor`. The rank is
param-independent (depends only on `p_da`), so it's built once at init.

### Day-type filter (stateful analogue of "run fully, filter")

SoC evolves over **every** ISP in the window (a weekend charge still affects the
following Monday); only totals / decomposition / counts / stats accumulate
matching-day ISPs. Because the filter gates accumulation rather than the SoC
*path*, `total(all) == total(workday) + total(weekend+holiday)` holds **exactly**
(locked by `test_daytype_partition_exact`).

### Parameter sensitivity — reading an optimum honestly

Not every optimised value carries the same information: a down-split rebalance
wait of 660 that loses only ~3 % when set to 24 is noise, not signal. After
every ⚡ Optimise (adding ~20 % to its runtime) the page therefore turns the
work the optimiser already did into an importance report — pure math in
`optim-sens.js` (`OptimSens`, **shared with the wind-park page**), mirrored
and locked in `tests_bess.py`:

**Local, one-at-a-time (OAT) at the found optimum** — each optimised parameter
is swept alone across its refine grid while everything else stays at the
optimum:

- **Weight** = worst % of revenue lost anywhere on that sweep. This is the
  honest "how much does getting this parameter wrong cost".
- **1 %-band** = the contiguous range of values staying within 1 % of the
  optimum. A wide band ⇒ the exact optimised value is interchangeable (the
  wait = 660 case reads: weight ≈ 0, band [1 … 672], shape flat).
- **Shape** = flat / ↑ higher-is-better / ↓ lower-is-better / ▲ interior peak,
  with a ✶ flag when a single grid step next to the optimum already loses
  > 5 % (handle-with-care cliffs).
- **⚠ edge** = the optimum sits on a sweep boundary — on this dataset that
  reliably flags the no-price-impact **liquidity levers** (`da_min_price`,
  `max_charge_price`), tying into the backtest caveat above.

**Global, over the seeded random population** — the 3 000 uniform random
samples the optimiser evaluated anyway:

- **Spearman ρ** (param ↔ revenue): the direction over the *whole* space, not
  just near the optimum.
- **Top-10 % cluster** = [q25 … q75] of the parameter among the best decile of
  samples: where good configs live; a cluster spanning the whole range means
  the parameter does not decide success.

**Interactions ("only works in tandem")** — parameter *pairs* ranked by
non-additivity: tertile-bin both parameters over the population, fit
grand + row + column effects to the cell means, score = count-weighted RMS
residual as % of the optimum. The strongest pair is then swept as a **2-D
heatmap around the optimum** (others fixed, ★ = the optimum) — a diagonal
ridge is the visual signature of two parameters that must move together.

Caveats (also on the page): OAT weight is only meaningful *at* an optimum
(measured from an arbitrary point, a parameter whose sweep only finds
improvements correctly reads ~0 — locked by a test); the population statistics
are correlational over independent uniform sampling, not a Sobol
decomposition; everything is deterministic (seeded RNG), so runs are
comparable. The report lives in the "Parameter sensitivity" card, is
per-session, and its top-3 drivers are persisted per run in the
Optimised-runs table.

### Why the discharge strategy re-prices instead of withholding

The original "dynamic discharge" implementation **withheld a fraction** of the
offer (dd_hold) when the price trend was rising. Measured on the full dataset
it was value-destroying: its trigger compared the *current* ISP's price with
the past (clairvoyant at gate time), so it fired exactly at spikes and held
half the volume back at precisely the best moments — Baltic mFRR spikes
mean-revert, so the held half sold into the fade.

The redesign never touches volume; it **raises the price**. The offer's ask
rests at `effCost + minDelta` and is reactively re-priced to
`last-settled + mark-up` (`p_mfrr[i−3] + dd_markup`) after a settled run-up
(`p_mfrr[i−3] − p_mfrr[i−3−lb] ≥ dd_threshold`). A rested offer forgoes the
whole ISP — the battery committed its power to it. On an isolated spike out
of a flat settled past the resting offer clears **in full** (no run-up ⇒
baseline ask; the old hold-back withheld exactly here) and the raised ask
then refuses to dump into the hangover unless the market beats the settled
level by the mark-up.

Measured on the FAIR-timing engine (full dataset, defaults elsewhere):

- re-pricing at lb 1 / thr 20 / mark-up 75 (shipped default): **+28.8 k€** vs
  mark-up 0 (2,109,994 vs 2,081,222 €) — under honest timing the raised ask
  genuinely earns; `mark-up 0` and `dd off` now coincide exactly, so the
  toggle isolates one clean mechanism.
- the old hard mFRR→aFRR switch ("route everything to aFRR when it paid more
  last ISP") was **removed**: under fair timing it measured **−72.7 k€**
  (trailing-window routing is the adaptive split's job; a 45-min-old one-ISP
  premium doesn't persist, and switching to aFRR costs partial-activation
  volume).
- a window-max ask base (`max` over the lookback + mark-up) was tested and is
  uniformly worse (too greedy — misses the many just-below-the-recent-high
  clears).
- the per-leg ask gate also fixed a latent quirk: previously a split-routed
  leg could clear **below** `effCost + minDelta` whenever the *other* market
  carried the `bestUp` gate.

For reference, the opportunistic divert measured as a fair bet contributes
**+104.6 k€** at the default threshold (with 56 misses paid for honestly);
these numbers supersede the pre-fair-timing ones, which were leakage-inflated.

### Per-ISP decision order

1. **Day-ahead** (committed a day ahead): discharge at a forecast peak (deliver from SoC; shortfall → imbalance) OR buy-low at a forecast trough.
2. **Direction pick** for leftover power (discharge vs real-time charge) on **known info only** — settled (≤ i−3) balancing prices and the live intraday quote — respecting the dwell cooldown: a flip to the opposite direction needs ≥ dwell idle ISPs since the last action (DA commitments exempt). Offers are placed whenever physically possible and rest if the market never reaches them.
3. **Discharge leg**: opportunistic divert (a committed bet — intraday buy-back paid, freed energy offered at `quote + threshold`; a miss keeps the energy and pays the spread) → set the ask (reactively re-priced on a settled run-up) → **up-split** routing to mFRR-up/aFRR-up, each leg clearing only if its realised price ≥ the ask.
4. **Real-time charge leg**: share the headroom by the **down split**, re-route lag-unusable sides, intraday only when settled balancing was dead; every order priced at the ceiling and cleared only by its own realised price.

### ⚠ Backtest caveat — DA / charge price levers saturate (no price impact)

Like the wind-park's `r_coef` / `X_cap`, the BESS backtest has **no
price-impact / market-clearing model**: offering more is always net-positive on
the frozen liquidity assumption. So the optimiser tends to drive `da_min_price`
toward its low floor (sell DA almost always), `da_charge_price` / `max_charge_price`
high (buy energy aggressively) — these are **liquidity levers**, not free money in
the real market. Treat them as constraints to set deliberately; the interior dims
(the split params, dwell, hold fraction) are genuine optima.

### Simplifications (documented, by design)

- **Whole-MW market volumes.** Every offer / commitment is floored to integer MW
  (the markets accept integer blocks only). aFRR's partial activation makes the
  *delivered* energy of a whole-MW aFRR offer a fraction (`n_*_fav/225`) — that
  part is intentionally fractional.
- **Initial energy is zero-cost.** The Initial SoC's cost basis is 0 (the gate
  `sell ≥ 0 + minDelta` is conservative anyway); over a 14-month run the initial
  20 MWh is negligible against the ~18 k MWh of throughput.
- **DA over-buy is not penalised.** A committed day-ahead buy charges only what
  fits in the battery; an un-storable committed buy (rare — we plan around the
  forecast) is dropped rather than modelled as an over-position. Day-ahead
  *discharge* shortfalls ARE penalised (the imbalance risk you care about).
- **Greedy controller, not an optimal-control solver.** Each ISP is dispatched
  greedily under the strategy gates — a faithful *strategy* backtest, not a
  perfect-foresight MILP.

**Winsorisation**: two independent percentile pairs (mFRR + aFRR, both
default 5 / 95). Both are applied to every sign-agreement count,
correlation, and scatter point. Without this, ±10 000 €/MWh outliers
in `p_mfrr` dominate the Pearson term and squash the scatter cloud to
a single pixel. Cap previews show the live clip values per direction
in the Setup card.

**Real findings** from the current dataset (defaults, slot-level):

- **Co-fire UP is strong, co-fire DN is weak.** ~64% of POS-direction
  4-s slots fall inside an mFRR-up ISP; only ~46% of NEG-direction
  slots fall inside an mFRR-dn ISP. The two markets agree more strongly
  on upward needs than downward.
- **Sign-agreement at slot level ≈ 49% for POS direction** — barely
  above what independence would predict (~46%). Slot-level disagreement
  is real, not a definitional artefact (audited via the directly-
  computed sign counts).
- **Pearson correlation ≈ 0.07 raw, ≈ 0.18 with 25/75 winsor.** The
  outlier-dominated raw number underrepresents the central correlation;
  the markets do move together, just weakly.
- **Interpretation**: mFRR-SA (15-min scheduled clearing on forecast
  errors) and aFRR (4-s automatic frequency restoration) respond to
  different signals at different timescales. They agree directionally
  most of the time but their pricing detail differs slot-by-slot.

### mFRR vs aFRR reserves sub-tab

Daily-aggregated **reserve (capacity) price** analysis from `data-reserve.js`
(LV mFRR/aFRR up+down hourly prices). Each market's daily value is the mean
over the window's matching-day ISPs of its winsorized up/down average — so
mFRR and aFRR each get **one value per day** (the user-requested
simplification from 96 ISPs/day). Setup: sim range, day-type filter, two
winsor pairs (mFRR / aFRR reserve price). It answers two questions:

1. **Do high reserve prices flag extreme-imbalance days?** Box plots of the
   day's mean |Baltic imbalance| binned by reserve-price quartile, one panel
   per market, plus `r(price, |imb|)`. Finding on the current data:
   **mFRR yes, aFRR no** — `r(mFRR price, |imb|) ≈ +0.30` (quartile medians
   climb 27→33 MW) while `r(aFRR price, |imb|) ≈ −0.10` (flat). mFRR capacity
   pricing anticipates system stress; aFRR pricing is driven by its own
   tail-heavy scarcity dynamics. (Combining the two markets washes the signal
   out — hence the per-market panels.)
2. **Do the two markets move together or play cat-and-mouse?** A dual time
   series, an aFRR-vs-mFRR scatter coloured by date, and the spread
   (aFRR − mFRR) over time. Finding: **not in unison** — level correlation
   ≈ −0.17 (mild substitution), day-over-day change correlation ≈ 0. The
   spread has **lag-1 autocorrelation ≈ 0.85**, i.e. it's **persistent
   regimes** (one product stays the better deal for stretches), not a fast
   daily oscillation. aFRR is the pricier product on ~46 % of days but its
   mean spread is +33 €/MW·h, pulled up by a fat upper tail (daily spikes to
   +287). The high persistence is exploitable: the recently-cheaper market
   tends to stay cheaper.

**Defaults:** the subtab opens on **01/01/2026 – 01/05/2026** with
winsorisation **off (0/100)** — the matured-market, fully-reserve-covered
window. The figures quoted above are the *full-dataset* view; widen the date
range to reproduce them. They're regime-dependent, which is the real lesson:
in the Jan–May 2026 default window the two reserve prices actually **co-move**
(level r ≈ +0.56, change r ≈ +0.52, near-equal levels) and **neither** predicts
imbalance (both r ≈ −0.09) — so the full-range mFRR-imbalance signal and the
aFRR "stability" pattern both lean heavily on 2025 (the latter on the Feb–Apr
aFRR-market startup specifically). Use the date filter to test robustness.

Two later additions to this subtab:

- **Capacity premium vs realized activation value** — the option-value lens.
  Each day: x = the DOWN capacity premium (daily mean price × 24,
  EUR/MW·day), y = a realized activation-payoff **proxy** for 1 MW offered
  all day (mFRR-dn: `0.25·Σ max(0, −p_mfrr)`; aFRR-dn: the same with the
  dispatched fraction `n_neg_fav/225` on `avg_p_neg`). The proxy ignores
  award probability and positive-price buy-backs — relative value, not P&L.
  Full-dataset reading: the premium runs several times the negative-price
  activation proxy (≈ 371 vs 84 €/MW·day for mFRR-dn; ≈ 276 vs 44 for
  aFRR-dn) and is nearly uncorrelated with it day-to-day (r ≈ 0.1 / −0.1) —
  capacity is priced as insurance, not as expected activation margin.
- **Structural-break markers** on every reserves time axis (and the daily
  charts of the Drivers tab): dotted red = **Baltic desynchronization from
  BRELL (8 Feb 2025** — three days after the dataset starts); shaded band =
  the **aFRR market ramp-up (Feb–Apr 2025)**. Pooled statistics blend these
  regimes; the markers keep that visible. They are drawn only when the
  plotted window overlaps them — Plotly does NOT clip out-of-range shapes,
  it *expands* a date axis to include them, which would graft an empty 2025
  region onto the default 2026 window.
- The option card's payoff proxy has its own **activation energy price
  winsor pair** in Setup (the raw mFRR series has ±10 000 €/MWh outliers —
  a single ISP could add 2 500 €/MW·day to one day's proxy); the premium
  axis respects the capacity winsor pairs.

### Drivers & timing sub-tab

The trader's complaint about the original tabs: they condition on forecast
*levels* and contemporaneous regimes, while balancing prices are driven by
**surprises and timing**. This tab (data: the optional `data-fund.js` from
`preprocess-fundamentals.py`, aligned to data.js indices by timestamp exactly
like data-reserve.js; math: `graphs-fund-engine.js` / `FundEngine`, mirrored
and locked in tests.py) adds six cards:

1. **Spread by forecast ERROR** — mFRR spread box-plotted by quantile bins
   of Baltic **wind error** (actual − DA forecast; the export prints mean
   ≈ −70 MW, σ ≈ 200 MW — Baltic wind is systematically over-forecast),
   Baltic **load error**, and the **pre-gate-knowable LV+LT wind DA→ID
   forecast revision** (Estonia publishes no intraday wind forecast, so the
   revision is defined on the LV+LT footprint and labelled as such).
2. **Hour-of-day & slot-in-hour** — the daily rhythm (median + IQR by UTC
   hour) and the **within-hour sawtooth**: hourly DA blocks vs continuous
   ramps make the :00/:15/:30/:45 ISPs systematically different (median
   spread and mean |imbalance| per slot).
3. **Monthly spike monitor** — share of ISPs beyond the up/down thresholds
   per calendar month + mean up-exceedance size, on **raw** prices. The
   non-stationarity monitor: drifting bars ⇒ pooled stats blend regimes.
4. **Lead–lag correlogram** — `r(series[i], spread[i+lag])` for aFRR-up avg,
   aFRR-dn depth and Baltic imbalance at lags −8…+8, with the **settled-
   information gate (lag ≥ 3)** shaded: bars there are *tradeable* under the
   backtesters' timing rules. Full-dataset reading: **aFRR-up leads the mFRR
   spread with r ≈ 0.27 at lag +3 — stronger than contemporaneous (≈ 0.14)**;
   Baltic imbalance leads with r ≈ −0.53 at lag +3 (deficit → high spread
   45 min later). The fast market moves first; the slow market follows.
   (NB: the aFRR series use the RAW averages — the graphs page never calls
   `Engine.maybeWinsorize`, so the winsorised working copies are zeroed
   there; raw is also the analytically right choice.)
5. **Conditional spike probability** — P(raw p_mfrr beyond X) by Baltic
   imbalance regime × wind-error tercile × UTC hour block, with counts and
   heat shading. Full-dataset reading at X = 200: **≈ 53% in
   deficit + wind-under-delivery cells vs ≈ 39% in deficit + over-delivery**
   — the surprise separates spike odds even within the same imbalance
   regime. (Regime and error are contemporaneous — the table explains; the
   revision chart is the knowable counterpart.)
6. **Merit-order scarcity & cross-zone divergence** — the LV accepted
   SA-mFRR **bid band** (daily width + where the clearing price sits inside
   it; the band widened from ≈ 26 to ≈ 155 €/MWh over the dataset) and the
   daily share of ISPs where LV decouples from EE / LT by more than a
   threshold — congestion episodes where LV-specific scarcity pricing
   appears.

Setup mirrors the other tabs (window / day-type / spread winsor pair) plus
error-bin count, up/down spike thresholds and the divergence threshold. Every
chart degrades to an in-chart notice if `data-fund.js` is absent; the timing
charts (2–5, regime-only table rows) work from the core dataset alone.

One item from the same review is **not** implementable in this repo:
archiving the bids-page `bids.json` snapshots into a growing merit-order
history requires a small append step in the private RetrievalTCK workflow
(this repo only *reads* that file).

### Day-type filter (Backtester and Graphs)

The Backtester's Setup box and each Graphs sub-tab have an independent
**day type filter** (All / Weekends + holidays / Workdays only).
Public-holiday detection runs through the `date-holidays` plugin for
**Latvia, Estonia and Lithuania** — a date counts as a holiday if any of
the three considers it a public holiday. (The Graphs mechanics are below;
the Backtester's run-fully-then-filter variant is described after them.)

Mechanics: `Engine.init()` builds a `dayTypeMask: Uint8Array`
(0 = workday, 1 = weekend, 2 = holiday) once at load time, classified
by UTC calendar date. Each engine layer (`GraphsEngine`, `AfrrEngine`,
`AfrrSpreadEngine`, `MfrrAfrrEngine`) reads the mask + the user's
filter state to skip non-matching ISPs in regime classification,
bin-edge derivation, and winsorisation percentiles. If the
date-holidays CDN fails the mask degrades to weekend-only (every
Mon–Fri counts as workday) and the engines log a console.info.

**Backtester day-type filter (run-fully-then-filter).** The same
control lives in the Backtester's Setup card, but the mechanics differ
because the P&L simulation is *sequential* (S3 intra-day oversell reads
a rolling window of preceding settled prices). Naïvely dropping
weekends *before* simulating would corrupt that rolling window at every
Monday boundary. So the Backtester always simulates **every** ISP in the
window continuously (the S3 rolling-stats cache is full-dataset, so a
Monday trade still "sees" the weekend's settled prices) and applies the
filter only as a **post-hoc accumulation gate**: `simulate` /
`simulateTotal` / `monthlyAggregation` / `totalPotMWhInWindow` sum only
ISPs whose `dayTypeMask` matches (`_dayAccepts`), and the optimiser
objective is that filtered total. Per-ISP arrays stay full so the
time-series chart simply gaps the hidden days. This is exact: each ISP's
P&L is independent of every other ISP, so the totals partition cleanly
(`total(all) == total(workday) + total(weekend+holiday)`, locked by
tests). "All days" is a strict no-op (frozen regression values
unchanged).

## Forecast — Baltic imbalance regime forecast

`forecast.html` + `forecast-app.js` + `forecast-charts.js`. Unlike the
Backtester and Graphs pages — self-contained and offline — the Forecast
page is a **thin client for a model that lives in a separate private
repository**. It ships no model and no data; it only reads the model's
output (`forecast.json`) and can ask the model to run again.

```
 this repo (public, GitHub Pages)  ──dispatch (GitHub API)──▶  private repo (model + runner)
        reads forecast.json         ◀──── read JSON ─────────         writes forecast.json
```

### What it shows

The model (`regime_v6_light_top100`) emits a **6-hour-ahead forecast in
24 × 15-minute steps**. For each horizon it predicts a probability over
three Baltic imbalance regimes plus an expected imbalance price:

- **NEG** — grid deficit (system short; needs upward energy).
- **ZRO** — balanced.
- **POS** — grid surplus (system long; needs downward energy).

Three views render from the same `forecast.json`:

1. **Probability per horizon** — stacked bar (`p_neg` + `p_zero` +
   `p_pos` = 1) per 15-min delivery slot.
2. **Expected imbalance price** — model-weighted expected price (solid)
   vs a calendar-only baseline (dashed). The gap is the value the model
   adds over a no-model expectation.
3. **Per-horizon detail** — the full numeric table, argmax cell bolded.

### Run flow (one shot per click — no auto-refresh)

Clicking **Run forecast** executes exactly one cycle and then returns to
idle. There is **no cron / interval loop**: a fresh forecast happens only
when the user clicks again.

1. Read the typed password from the field.
2. `unlockPAT(password)` — PBKDF2-derive an AES-GCM key and decrypt the
   `ENCRYPTED_PAT` blob. Wrong password → AES-GCM auth-tag mismatch →
   surfaced as "wrong password"; the field clears and nothing is fetched.
3. `dispatchWorkflow(password)` — `POST …/actions/workflows/<file>/dispatches`
   with `inputs.password`. The workflow's **first step** re-checks that
   password against a server-side secret (`RUN_PASSWORD`) and auth-fails
   fast (~5 s) if it doesn't match — so leaking the PAT alone doesn't let
   anyone burn compute.
4. `waitForRunCompletion` — poll every **5 s** (`POLL_INTERVAL_MS`) until
   the run completes, giving up after a **15-minute** timeout
   (`POLL_MAX_MS`).
5. `fetchAndRender` — read `forecast.json` via the Contents API and
   redraw all three views.

While a run is in flight the button becomes **Cancel** (aborts the
in-flight poll). The typed password stays in the masked field between
runs so a re-run is a single click; it is never written to disk, browser
storage, or the URL, and a reload clears it. The decrypted PAT is dropped
from memory the moment a run ends — success, failure, or cancel.

On a successful `fetchAndRender`, the completed forecast **output** (and
only the output — never the PAT or password) is cached to
`sessionStorage` (`tck.forecast.v1`). On page load the charts + table are
restored from that cache with **no network call and no PAT**, so leaving
the page mid-session and coming back doesn't lose a finished 15-minute
run. A run takes ~15 min, so this matters. The header's "Last forecast: N
min ago" reflects the cached `generated_at`, and the status reads
"restored last forecast". See [Per-tab caching](#per-tab-caching).

### Per-tab caching

Both the Backtester's **Optimised runs** log and the Forecast page's last
result are persisted in **`sessionStorage`** — deliberately *not*
`localStorage`. `sessionStorage` survives same-tab navigation and reload
but is cleared when the tab closes, which matches the intent: "keep my
work while I bounce between pages, but don't resurrect a stale run
tomorrow." Keys are version-suffixed (`…​.v1`) so a future shape change
can invalidate old caches, and every read/write is wrapped in try/catch
so a disabled or full store degrades gracefully to in-memory behaviour.
Nothing sensitive is stored: the forecast cache holds only model output,
and the PAT / run password are never persisted anywhere.

### `forecast.json` schema

A single JSON document, committed at the root of the private repo:

```jsonc
{
  "generated_at": "2026-06-05T09:30:00Z",  // ISO; drives the "Last forecast: …" header
  "error": null,                            // optional; a non-null value short-circuits render
  "horizons": [
    {
      "h": 1,                               // 1…24
      "minutes_ahead": 15,
      "delivery_time": "2026-06-05T09:45:00Z",
      "p_neg": 0.21, "p_zero": 0.54, "p_pos": 0.25,  // sum to 1
      "argmax": 1,                          // index of the most likely class
      "argmax_label": "ZRO",                // "NEG" | "ZRO" | "POS"
      "expected_imbalance_price_eur_mwh": 38.4,
      "expected_imbalance_price_baseline_eur_mwh": 41.0
    }
    // … 24 entries
  ]
}
```

If `error` is present the page shows it in the status line and leaves the
last successfully-rendered charts untouched.

### Configuration (before the page works)

Everything the page needs is at the top of `forecast-app.js`:

| Constant            | Meaning                                                         |
| ------------------- | --------------------------------------------------------------- |
| `REPO_OWNER`        | Owner of the private model repo.                                |
| `REPO_NAME`         | Private model repo name.                                        |
| `WORKFLOW_FILENAME` | Workflow file under `.github/workflows/` (e.g. `forecast.yml`). |
| `FORECAST_PATH`     | Path to `forecast.json` within the repo (root by default).      |
| `ENCRYPTED_PAT`     | `{ iterations, salt, iv, ciphertext }` — generated below.       |
| `POLL_INTERVAL_MS`  | Poll cadence after dispatch (5 s).                              |
| `POLL_MAX_MS`       | Give-up timeout for a single run (15 min).                      |

To (re)generate `ENCRYPTED_PAT`, open **`encrypt-pat.html`** under
`file://` — it is local-only (no network, nothing written to disk):

1. Paste a GitHub **fine-grained PAT** (scopes on the private repo:
   Actions read+write, Contents read).
2. Choose a long shared password (≥ 12 random characters). This is what
   the team types into the Forecast page **and** what the workflow's
   `RUN_PASSWORD` secret must equal.
3. Keep PBKDF2 iterations at ≥ 600 000 (OWASP-2023 floor for SHA-256 —
   ~1 s per decrypt, i.e. ~1 s per attacker guess).
4. Copy the emitted `const ENCRYPTED_PAT = { … };` snippet over the
   placeholder in `forecast-app.js`.

Rotating the PAT or changing the password is just a re-run of
`encrypt-pat.html` with the new value, then re-pasting the snippet.

### Security model

| Where                         | What is / isn't there                                                                                  |
| ----------------------------- | ------------------------------------------------------------------------------------------------------ |
| Public repo (this one)        | Only the `ENCRYPTED_PAT` blob (random-looking base64). **Never** the PAT plaintext or the password in any form. |
| Browser memory (during a run) | The decrypted PAT (dropped when the run ends) and the typed password (masked field; cleared on reload). |
| Private repo / Actions        | The `RUN_PASSWORD` secret — the independent server-side gate.                                          |

The protective strength is whatever entropy the password has: PBKDF2
(SHA-256, ≥ 600 k iter) makes each guess cost ~1 s, and AES-GCM gives a
clean wrong-key signal. Even if someone breaks the client-side
encryption, the workflow's password gate still rejects unknown callers in
~5 s.

> ⚠ This is **defence in depth, not strong secrecy.** Anyone holding the
> shared password can both decrypt the PAT and trigger runs, so treat the
> password as the real credential — keep it out of chat logs and rotate
> it like one.

## European date format

Date inputs are `<input type="text" placeholder="DD/MM/YYYY">` with an
explicit regex pattern, NOT `<input type="date">`. The browser's
native picker is locale-driven and disagrees with users on the
DD/MM/YYYY vs MM/DD/YYYY rendering — text inputs guarantee the
DD/MM/YYYY display everywhere.

Internally the canonical form is still `YYYY-MM-DD` (ISO).
`parseEU(str)` and `isoToEU(iso)` handle the round-trip and accept
`/`, `.`, `-` separators on input. Plotly's tickformat is set to
`"%d/%m/%Y"` for any time axes.

## Data refresh workflow

Replace any of the source CSVs and re-run the matching preprocessor(s):

```
python preprocess.py                # if main_data_with_imbalance.csv changed
python preprocess-afrr.py           # if ast_afrr_data.csv changed (counts + chunked spread)
python preprocess-afrr-15min.py     # if ast_afrr_data.csv changed (averaged 15-min prices)
python preprocess-reserve.py        # rebuild data-reserve.js (reserve prices)
python tests.py                     # see "frozen regression values" caveat below
```

What re-derives **automatically** from the new datasets:

- Date range header text (DD/MM/YYYY)
- Sim-range and chart-range input bounds (data min/max dates)
- Quantile bin boundaries on every Graphs render
- Winsorisation bounds + cap previews (computed within the sim window)
- All chart axes / tooltips / aggregations
- Naïve baseline — the true do-nothing floor: X=Y=Z=0 and **every strategy
  neutralised** (DA-withhold, ID-trust, S3, reserve, and the split → all-mFRR),
  at the current θ + sources. So "vs naïve" shows the combined lift of every
  enabled strategy, including the adaptive split (it no longer absorbs the
  split's gains into the baseline).
- Backtester decompositions, robustness stats, monthly bars
- ISP counts (mFRR + aFRR per direction, regime / dead-band)
- Day-type mask + holiday set (recomputed once at `Engine.init`)

What needs **manual attention** when the data changes substantially:

- **`tests.py` regression values** are frozen on the current dataset:
  - L1 default = 13,257,221 €
  - L2 default = 13,367,642 €
  - L3 default = 15,185,134 € (S3 on, reserve off, split all-mFRR)
  - April-row count = 2,880
  - ~2,911 NaN p_imb entries

  After a data refresh these need updating — `python tests.py` will
  tell you which assertions need new values, then re-freeze them.
- **Reserve-price backfill.** The source CSV's reserve columns had no
  data for Oct–Dec 2025; that gap was patched in from the official
  procured-reserves export. If you regenerate `main_data_with_imbalance.csv`
  from upstream, **re-apply `scratch/patch_reserves.py`** (or the quarter
  goes blank again) before `preprocess-reserve.py`.
- **Cache-busting `?v=N`** in `index.html` and `graphs.html`. Bump N
  when deploying so users re-fetch updated data / JS / CSS.
  Conventionally `index.html` and `graphs.html` use independent
  numbering (graphs has more files to invalidate, so its `v` runs
  ahead).
- **mFRR up vs down assumption**: code uses `mfrr_sa_upward_lv` and
  assumes `mfrr_sa_downward_lv` matches it (99.85 % in current data).
  If a refreshed CSV breaks that, re-evaluate the assumption.

If the refreshed CSV's column names change, both `preprocess.py`
`NEEDED` and `tests.py` `usecols` need to be updated — they fail loud
with `KeyError` rather than silently producing wrong numbers.

## Known quirks (for future agents)

These are non-obvious behaviours by design — read before "fixing".

1. **NaN `p_imb` → 0 imbalance cost.** April-2026 rows have no source
   imbalance price (the upstream file ends in March). The engine
   keeps those rows in the simulation (DA + mFRR revenue still
   accrues) but zeros their imbalance + flat-penalty contributions.
   This UNDERCOUNTS L2 cost if you pin the sim window to April only.
   When a future CSV provides April imbalance prices, `p_imb` simply
   stops being NaN and the cost flows through — no engine change
   needed. Behaviour is in `simulate()` / `simulateTotal()` /
   `monthlyAggregation()` (each guards independently — check
   `tests.py` "April ISPs: NaN p_imb → 0 imb cost in L2" if you
   refactor).

2. **Whole-MW market quantities lose fractional MW.** Forecasts come
   in as floats (e.g. 7.2 MW) but the balancing market accepts only
   integer MW. We `floor()` `Q_da_sold`, `Q_w`, `trusted_rev`, and
   `Q_dn_offer`. Up to 1 MW per ISP is therefore "untraded" by the
   strategy — visible mostly with very small forecasts (F < 5 MW).

3. **mFRR-dn capped at `Q_da_sold`, NOT `Q_w`.** A wind park can
   curtail down from its DA position to zero; it cannot go negative.
   When `Q_da_sold = 0` (e.g. Y=1 below X) there is no mFRR-dn
   revenue at all. This was an audit fix — earlier versions of the
   code allowed phantom mFRR-dn revenue with no DA position. See
   `tests.py` "mFRR-dn capped at Q_da_sold".

4. **`Q_position = Q_da_sold + Q_up − Q_dn`.** When mFRR-dn fires,
   the curtailment reduces our promised production. The `−Q_dn` term
   is critical for shortfall accounting to be correct.

5. **mFRR up == down assumption.** `engine.js` uses
   `mfrr_sa_upward_lv` as the canonical mFRR clearing price.
   `mfrr_sa_downward_lv` matches it in 99.85% of rows in the current
   data (i.e. they are the single clearing price). If a future
   dataset breaks this, the engine silently uses upward only.

6. **DA price shared across LV/EE/LT.** We use
   `lt_dayahead_price_eur_mwh` as the price for the Vanessa park
   (Latvia). If LT/EE/LV ever decouple, this needs revisiting.

7. **Browser cache.** Static-server caching is aggressive. The
   `?v=N` query string on `<script>` and `<link>` tags is the manual
   cache buster — bump `N` after a deploy.

8. **`<input type="text">` for dates.** Native `<input type="date">`
   is locale-driven and shows MM/DD/YYYY on US-locale browsers
   regardless of `lang="en-GB"`. We use text inputs with explicit
   DD/MM/YYYY parsing instead. Trade-off: no native calendar picker.

9. **Engine window is global.** `Engine.setWindow(start, end)` is
   module-level state shared across both pages. Both pages call it
   inside their respective `update*()` paths — so the most recent
   page's window "wins" until the other page re-runs. Currently fine
   because rendering is synchronous; not safe for hypothetical
   parallel async sims.

10. **Plotly via CDN.** No SRI hash (Plotly's CDN doesn't publish
    one). If `cdn.plot.ly` becomes unreachable, the site degrades to
    a blank page; charts fail silently. Worth pinning to a vendored
    copy if you care about offline robustness.

11. **aFRR favourable-only filter is applied AT PREPROCESS TIME, not
    runtime.** Inside a single 15-min ISP, the 4-s prices can swing
    sign — e.g. AST_NEG values `{−10, +50, NaN×223}`. Naïve averaging
    gives `+0.18 €/MWh`, the engine's `avg_p_neg < 0` gate then drops
    the entire ISP, and we lose the favourable-slot earnings. The
    fix is in `preprocess-afrr-15min.py`: AST_POS values ≤ 0 and
    AST_NEG values ≥ 0 are replaced with 0 BEFORE the sum. So
    `avg_p_pos ≥ 0` and `avg_p_neg ≤ 0` dataset-wide BY CONSTRUCTION.
    `n_pos_fav` / `n_neg_fav` are the matching favourable-slot counts
    that scale the L2 position contribution. If you ever change the
    averaging logic, also revisit the synthetic mixed-sign test
    `test_afrr_15min_filter_recovers_mixed_sign_isp` in `tests.py`.

12. **`s_up` and `s_dn` are independent on purpose.** The mFRR-vs-aFRR
    economics differ between directions (mFRR-up clears only on upside
    spikes, aFRR-up earns continuously on positive avg; mFRR-dn fires
    when the system needs to curtail at negative prices, aFRR-dn earns
    when AST_NEG goes negative). On the current dataset the optimiser
    settles at `s_up ≈ 0` (route upward to aFRR) and `s_dn ≈ 1` (keep
    downward in mFRR). A single shared `s` parameter would lose
    ~150 k €/yr of "easy" asymmetric optimum — DO NOT collapse them.

13. **aFRR profitability gate at ISP granularity.** mFRR has a binary
    per-ISP gate (`|P_mfrr| ≥ 1`); aFRR has a similar gate per direction
    (`avg_p_pos > 0` for upward, `avg_p_neg < 0` for downward). When
    the gate fails, the offered volume earns 0 AND contributes 0 to
    the L2 position — the wind park simply didn't bid that direction
    this ISP. This is the "smart bidding" model; without it, an
    unfavourable ISP would generate negative aFRR revenue (the wind
    park paying for the privilege of being curtailed) and the
    optimiser would just learn to stay in mFRR universally.

14. **Day-type filter holidays via CDN plugin.** `date-holidays` v3.28
    is loaded from jsdelivr only on `graphs.html`. The UMD bundle
    exposes `Holidays.default` (NOT `Holidays` directly — newer
    ES-module-flavoured wrapping). `engine.js` probes both shapes.
    If the CDN fails entirely, `Engine.init` logs a console.info and
    falls back to weekend-only classification (every Mon–Fri counts
    as workday). Holiday dates are matched by UTC calendar date — a
    couple of hours of LV/EE/LT timezone slack are absorbed by the
    15-min ISP resolution.

15. **aFRR bar-chart resize on tab switch.** The Graphs page
    pre-renders the 3 aFRR activation-bar charts ~200 ms after page
    load (so switching to the aFRR tab feels instant). Plotly draws
    them into a panel that's still `display: none`, ending up with
    0×0 canvases. The fix is in `graphs-app.js`'s tab handler: after
    activating a panel, it calls `Plotly.Plots.resize` on every
    `.chart` in it. Idempotent and safe on un-rendered charts.

16. **Time-series chart shows 4 bar stacks per direction.** mFRR-up
    (dark green), aFRR-up dispatched (light green), mFRR-dn (dark
    red), aFRR-dn dispatched (light red), with `barmode: "relative"`
    so the same-sign bars stack. The aFRR bar height is the
    DISPATCHED MW (`Q × n_*_fav / 225`), not the offered MW — so a
    30 %-active ISP shows a 30 %-tall bar. The tooltip likewise shows
    offered + dispatched + dispatch-fraction-of-ISP per direction.
    L3 adds two more bars per direction with `marker.pattern.shape =
    "/"` diagonal hatching: **S3 ID oversell** (green hatched, positive
    y) and **S3 hedge curtail** (red hatched, negative y, only when the
    hedge mFRR-dn bid clears). The tooltip's `ISP P&L` line is rendered
    as a colour-coded equation breakdown (e.g.
    `<span style="color:green">150</span> + 30 − 24 = +156 €`) so the
    user can read which components contributed.

17. **S3 hedge mFRR-dn bid is a stop-loss, NOT a windfall trigger.**
    The hedge is an mFRR-dn offer the wind park wouldn't normally place
    — pitched above the typical clearing — so it costs the park when it
    clears, but bounds the loss on the oversold MW. The activation
    condition is `p_mfrr ≤ bid_price` (where `bid_price = VWAP1H + M`,
    typically a positive number). This means the bid clears whenever
    the mFRR-dn marginal price isn't above our ceiling — which includes
    both the windfall case (`p_mfrr < 0`, grid pays us) AND the
    bounded-loss case (`0 < p_mfrr ≤ bid_price`, we pay up to
    `bid_price` per MWh). The earlier draft of S3 had the activation
    condition flipped (`p_mfrr ≤ −bid_price`) which only fired in the
    windfall sub-case; that bug is fixed and the verification trail
    lives in the slot-level comparison's co-fire numbers (hedge clears
    ~89% of S3 oversells at defaults, vs ~6% under the wrong sign).

17b. **S3 imbalance settlement is decomposed but mathematically equivalent
     to one line.** When the hedge bid doesn't clear and the wind park
     ends short, the engine splits the cost between three rows:
     `imb = short_l2 × p_imb`, `flat = short_l2 × θ`,
     `s3_extra_cost = (short − short_l2) × (p_imb + θ)`. By construction
     this sums to `short × (p_imb + θ)` — i.e. exactly the naïve
     "total short at the imbalance settlement price" cost, no double-
     counting, no omission. The decomposition exists so the L3 stats
     panel can attribute cost to L2 vs S3 separately, not because the
     economics differ. Two consequences worth knowing:
     - When `p_imb` is NEGATIVE (system pays the park to be short),
       `s3_extra_cost` goes negative → S3 oversell becomes a windfall,
       because the wind park profits from the shortfall it created.
     - When `p_imb` is NaN (April-2026 rows), all three terms are
       zeroed in lockstep — S3 looks artificially profitable in those
       windows. The L2 NaN-handling caveat (Known quirks #14) extends
       to S3.
     Both behaviours are tested in `tests.py`
     (`test_s3_imbalance_decomposition_equals_naive_short_cost`,
     `test_s3_nan_pimb_zeroes_all_imbalance_terms`).

17c. **`S_min = 0` makes the proportional-sizing formula degenerate.**
     The S3 sizing rule is
     `X_prop = floor(X_cap · min(1, (spread − S_min) / S_min))`.
     When `S_min = 0`, the inner division is `spread / 0 = ±∞`; with a
     positive spread `(spread − S_min) / S_min = +∞ → min(1, ∞) = 1`, so
     `X_prop = X_cap` whenever the spread is positive (gates G2/G4 still
     apply). This is a *feature*, not a bug — it means "no minimum
     spread; just always go full size" — but it makes `S_min` a step
     function around 0. Avoid `S_min = 0` in serious analysis; use
     `S_min ≥ 1` if you want a smooth size response.

17d. **S3 can sell at negative `VWAP1H` if `mean(past p_mfrr)` is more
     negative.** The spread gate uses `spread = VWAP1H − mean(past
     p_mfrr) ≥ S_min`. In ISPs where the recent mFRR settled deeply
     negative (e.g. −100 €/MWh during a series of mFRR-dn clearings),
     even a slightly negative `VWAP1H` (say −5 €/MWh) yields a positive
     spread of +95, so S3 fires. The strategy then SELLS at `VWAP1H` =
     −5 €/MWh — i.e. pays the intra-day market €5/MWh to take the
     power. Whether this is a real opportunity or a data artefact
     depends on the use case; the audit found such ISPs in the dataset
     (e.g. ISP 10349, 2025-05-24 11:15). If a live strategy should
     refuse to sell at negative prices, add a gate `bid_price > 0` or
     `VWAP1H > 0` outside the engine.

18. **Some dims are held fixed (physical / liquidity constraints).** The
    optimiser sweeps the enabled strategies' levers (reserve-up
    `ru_coef`/`ru_split`/`ru_min_mw`, reserve-down `r_coef`/`r_split`,
    `X`, `Y`, the six adaptive-split params, `Z`, S3 `K`/`S_min`/`σ_max`/`M`)
    but holds **both min reserve prices** and S3 **`X_cap` / lag `L` /
    `DA_skip`** at the user's values — they're physical / liquidity
    constraints, not strategy levers. `X_cap` in particular is excluded
    because the backtest has **no price-impact term** — selling more is
    always net-positive on this dataset's frozen liquidity assumption, so
    sweeping `X_cap` would just pick the grid max every time. The reserve
    **`coef`** dims (`r_coef` and `ru_coef`) ARE swept but **saturate
    to 1.0** for the same reason (no price-impact / auction-clearing model) —
    treat them like `X_cap` and lean on the min reserve price (and, for up,
    `ru_min_mw`) to gate participation. Note up `ru_coef → 1.0` means
    selling *nothing* to DA (all forecast held as upward reserve), which the
    real auction would not clear; gate it deliberately. Interior dims (`K ≈ 2-4`,
    `M ≈ 0-5`) are genuine optima; `S_min` and `σ_max` may still
    settle on grid edges where the gates never trip (`σ_max ≈ 900-950`
    on the current data — the rolling-std rarely gets that high so
    σ_max in that range is in a flat region of the objective). Live
    trading must set `X_cap` from a real price-impact / liquidity
    model. The formula correctly identifies *when* to oversell; only
    the *size* needs an outside input.

19. **mFRR vs aFRR comparison is slot-level by default.** When the
    user opens the "mFRR vs aFRR" Graphs sub-tab, `graphs-app.js`
    triggers `loadAfrrPriceData()` if not already loaded; meanwhile
    the ISP-level fallback renders so the page isn't blank. Once the
    4-s file finishes loading, `loadAfrrPriceData`'s onload callback
    calls `scheduleCmpUpdate()` to swap the charts to slot-level
    automatically. In slot mode, `p_mfrr` is broadcast 225× per ISP
    — so n inflates but effective independent observations stay at
    ~n_ISPs. The correlation tile flags this explicitly.

20. **`p_mfrr` direction is inferred from sign at thresholds ±1.**
    The CSV has separate `mfrr_sa_upward_lv` and `mfrr_sa_downward_lv`
    columns but they're equal in 99.85% of rows (single-clearing-price
    market in Latvia). `engine.js` reads `mfrr_sa_upward_lv` as
    `p_mfrr` and classifies direction by sign vs ±1: this is
    equivalent to the wind farm placing standing bids at "I'll
    provide upward for at least +1 €/MWh" and "I'll curtail for at
    least 1 €/MWh paid to me" (= bid threshold −1). Under the unified
    pricing model these are mutually exclusive per ISP (no overlap
    between the +1 and −1 sides). **Note**: "mFRR-up fires" in the
    code means "the wind farm's mFRR-up bid clears" — NOT necessarily
    "the system needed upward globally". The two are nearly the same
    for our park's strategy but not identical.

## Deploying to GitHub Pages

1. Push this repository to GitHub.
2. **Settings → Pages → Source:** "Deploy from a branch", **Branch:**
   `main`, **Folder:** `/ (root)`.
3. The site will be live at
   `https://<username>.github.io/<repo>/index.html`. The Graphs page
   is at `/graphs.html` and the Forecast page at `/forecast.html`.

The site uses cache-busting `?v=N` query strings on every script /
stylesheet reference, so bumping `N` in `index.html`, `graphs.html`, and
`forecast.html` forces clients to re-fetch after a deploy. `N` is tracked
**per page** (each page's references share one number), so bump only the
page whose assets changed.

**The Forecast page additionally needs a configured private model repo.**
Fill in the constants and `ENCRYPTED_PAT` in `forecast-app.js` (see
"Forecast"), and set the `RUN_PASSWORD` secret on the workflow in that
private repo. Until then the page deploys fine but stays blank ("idle —
enter password to begin"). `encrypt-pat.html` is a local-only helper and
need not be deployed.

## Performance

- All numeric arrays are converted to `Float32Array` at load time.
- Winsorized arrays are cached and re-derived only when bounds /
  window / day-type filter change. Cap values are returned even on
  cache hits so the live preview can update without recomputing.
- Backtester optimiser cost (random + multi-start refine, see
  "Unified optimiser" above):
  - L1: N=2000 random + 3 refines → ~2.5 s wall on the current dataset.
  - L2: N=4000 random + 3 refines → ~7 s wall.
  - L3: N=4000 random + 5 refines → ~23 s wall (refines dominate at
    9 dims, so the bar pauses at the refine boundary; the inner loop
    still yields every 200 ms so the UI stays responsive).
  - Cooperative yields via `MessageChannel.postMessage` (the
    `setTimeout(0)` clamp / background-tab throttling makes
    `setTimeout`-based yields ~50× slower in some browser contexts).
- Time-series chart: bar mode for ranges ≤ 600 ISPs (~6 days),
  scattergl for longer windows. Full-dataset render (43 k points,
  4 stacked bar series) in ~1.7 s.
- Graphs page: full re-compute (7 box-plot / heatmap charts) in
  ~250 ms; aFRR price plots reuse a cache keyed on (window × bins ×
  winsor × day-type) so toggling direction doesn't re-walk the 8.5 M
  per-4-s entries.
- `Engine.init` builds `dayTypeMask` once at page load (~1 ms for
  43 k ISPs); it's a pure function of timestamps so no recomputation
  is needed when the user toggles the filter.

Plotly is loaded from `cdn.plot.ly` and date-holidays from jsdelivr —
both via versioned URLs. Neither CDN publishes SRI hashes, so the
script tags have none.
